# Performance baseline — 2026-11-23

Measured at `a8c7b13`, after the 2026-11-16 audit fixes (APP-02, PERF-01..03).

## Summary

- **Opening a Review is the slowest thing a user waits for:** 0.57 s (50 files), 0.78 s (one 20,000-line file), 1.43 s (5,000 files / 300 changed), and 3.7 s on the same repo when Git's index is stale. After the start command, three reads run one after another, and each one checks the whole working tree again.
- **Every snapshot read checks the working tree with 7 Git processes:** `review.manifest`, `review.diff` and `review.questions` each take 65–75 ms on a tiny repo and ~150 ms on the large one, even when nothing changed.
- **The first search in a Review takes 2.7 s** on the 20,000-line file (0.75 s on the large repo). The State worker re-hashes the whole file for every 64-row window it reads.
- **Each keypress rebuilds the whole screen** (200–265 OpenTUI objects): 15–20 ms per keypress after a pause (often a missed 60 fps frame), 5 ms when the CPU is already busy. Wheel scrolling holds 60 fps.
- **No leak of old screen trees:** after 4,800 keypresses the heap and object count stay flat. Live recapture after an edit takes 0.2–0.6 s. With a Review open, the runtime runs 7 Git processes every 2 s while idle.

## Method

- **Machine:** Apple M4 Pro, 12 cores, 48 GB, macOS (Darwin 27.2.0), Node 26.5.1, `@opentui/core` 0.9.1, heavy antivirus scanning. Load averages during runs ranged from 4.5 to 14. The final UI set ran at 4.6–7.3.
- **Repositories** (synthetic and disposable, generated by `scripts/perf-probe/makeRepos.mjs`):
  - *small*: 50 files of 120 lines. 5 changed: 4 modified, 1 added.
  - *large*: 5,000 files of ~150 lines in 250 folders. 300 changed: 260 modified, 25 added, 15 deleted (+3,380 / −5,630 lines).
  - *hugefile*: `big.ts` has 20,000 lines with every 10th line edited. `longlines.js` has 400 lines of 2,000 characters with 58 edited. 20 files are unchanged.
- **How:** the UI was driven by the real app through `createTestRenderer` (160×48, kitty keyboard, mouse) and `createReviewingApplicationForTest`. The production path used `openDeveloperWorkspaceRuntime`, so a real detached runtime process talked to the app over the socket ("ipc"). Each Workspace read was also timed with an in-process owner, with and without a live subscription (the app always holds one once a Review is open). Each repo copy was a fresh APFS clone with no State. The Git index was refreshed after cloning unless the run was marked "stale index".
- **What the numbers mean:**
  - "Key → frame" runs from `mockInput.pressKey` until the first presented frame whose text changed.
  - "Draw" times `ShellRenderLoop.render` (whole-tree replace), wrapped from outside.
  - `nativeSceneVerify` was off. The test renderer turns it on by default, and it adds debug work.
  - Terminal paint is excluded.
- **Profiles:** `node --cpu-prof` of the TUI, the runtime and an in-process Workspace; dist lines mapped to `src`.
- **Isolation:** all three XDG dirs pointed at temporary dirs.
- **Reproduce:** probe scripts are in the worktree `.claude/worktrees/agent-a1134c05eaa4f2e2e/scripts/perf-probe/` (uncommitted). After `nvm use` and `pnpm build`:


## Ranked findings

### 1. Opening a Review re-checks the working tree three times in a row

- **How much:** large repo 1.43 s (3.7 s with a stale index), small 0.57 s. Of that, 0.6 s (1.6 s stale) is three back-to-back full verifications after the start command already captured everything.
- **Where:**
  - `reviewingApplication.ts:915` `#readReviewBundle` awaits the bundle (`:920`), then `review.live-files` (`:1015`), then the Diff (`:1081`), one after another.
  - `projection/index.ts:2590-2600` reuses a finished verification only while a live subscription exists (`watching`). The app subscribes after this first load.
  - Each step therefore runs `#verifyLiveChangesNow` (`:2620`), which calls `stillDescribes`, which runs the evidence `#verify` (`workspaceEvidence/index.ts:1050`), all over again.
- **Why:** `adoptLiveCapture` (`projection/index.ts:2554`) keeps the start command's capture, but not as a settled verification. Each read in the open sequence pays for a full `git status` and related work again.
- **Fix:** do both of the following.
  - Record the adopted capture as a settled verification for the current live generation. The watcher and fallback still bump the generation, so the truth rule holds.
  - Issue `review.live-files` together with the bundle read, and the Diff as soon as its file is known.
- **Expected gain:** −0.4 to −0.6 s on large (−1.5 s stale), about −0.2 s on small.
- **Risk:** low to medium. Current, stale and unverified must still come only from a check at the current generation.

### 2. Every snapshot read runs a full working-tree verification

- **How much:** 7 Git processes, 65–75 ms on a 5-file repo, ~150 ms on the large one, even with the live subscription open.
- **Where:**
  - `projection/index.ts:1266` `#snapshotStatus` and `:1283` `#readSnapshotStatus` call `workspace.current-changes.verify`.
  - The callers are `#manifest` (`:1572`), `#diff` (`:3081`, `:3114`) and `#questions` (`:3615`).
  - `#snapshotStatusReads` only merges reads that happen at the same moment (`:1270-1279`).
- **Why:** the header's current/stale status is recomputed for every read. That covers each Review refresh after a commit or Send, Snapshot and history views, and every Diff window of a fixed (commit or range) Review.
- **Fix:** cache the status per Snapshot identity and live generation, cleared by the same events that clear live verifications (watcher, fallback tick, `publishCommittedVersion`).
- **Expected gain:** 150 ms → ~1 ms per such read.
- **Risk:** low. It follows the same invalidation rules as the live reads, which are already trusted.

### 3. A stale Git index makes every check 15× slower, forever

- **How much:** `git status` takes 366 ms instead of 25 ms on 5,000 files. Opening takes 3.7 s instead of 1.4 s. Every 2 s fallback tick pays the same cost.
- **Where:** `gitProcess.ts:898` sets `GIT_OPTIONAL_LOCKS=0`, so Git never writes refreshed stat data back to the index.
- **Why:**
  - When many files' stat data changes without their content changing, Git re-reads and re-hashes each such file on every status call. This happens with agent rewrites, formatters, copies, `touch`, and some branch tools.
  - BuildFrame never lets that refresh land. It is right not to write the user's index, but then the cost never goes away.
- **Fix:** keep a private copy of the index under the runtime's temporary inspection overlay (`GIT_INDEX_FILE`). Re-copy it when `.git/index` changes, and let `git status` or `update-index --refresh` write refreshed stat data into the copy.
- **Expected gain:** ~340 ms per check on affected repos.
- **Risk:** medium. The copy must be atomic, and split-index, sparse index and the `sparseCanonical` fingerprint (`enumeration.ts:67`) must still be honoured.

### 4. The first search re-hashes whole files for every 64-row window

- **How much:** 2.7 s on the 20,000-line file, 0.75 s on 300 files. Later searches take ~90 ms.
- **Where:**
  - `projection/index.ts:3438` `#buildSearchIndex` reads one 64-row window per call (`#diffRows` `:3208`, `#searchRowTexts` `:3535`). That is 625 State worker round trips for 40,000 rows.
  - In the worker, `readContent` (`authoritativeStateWorker.ts:1588`) first runs `scanRecordQuarantineCandidates(…, true)` (`:570`) → `recordContentForValidation` (`:508`) → `digestBytes` (`:143`) over the entire record content. It then reads and digests the same blob again.
  - The worker profile shows `readContent` taking 2.3 s of the 2.7 s.
- **Why:** each call checks integrity for the whole record, so cost grows as windows × file size. Snapshot Diff paging through `#diffText` pays the same per window on fixed Reviews.
- **Fix:** build the search index from one whole-side read per file, slicing rows by `byteOffset`. In the worker, validate each digest at most once per call, or remember validated digests for the current State version.
- **Expected gain:** 2.7 s → ~0.2 s.
- **Risk:** low. The integrity checks stay; they just stop repeating.

### 5. Each keypress rebuilds and re-creates the whole screen

- **How much:** a draw takes 15–20 ms (p90 21–25, max 38) on an isolated keypress, so key → frame is 20–24 ms and often misses a 60 fps frame. A warm CPU does the same work in 5 ms, and wheel draws take 4 ms.
- **Where:**
  - `reviewingView.ts:5067` `#renderNow` → `shellRoots.ts:48` `mount` → `renderTree.ts:37` `mount`/`create`. The cost is in OpenTUI constructors: `TextRenderable`, `BoxRenderable`, `setupYogaProperties` (`@opentui/core` chunk `:15816`, `:11351`, `:8631`).
  - The tree description is `reviewingView.ts:4723` `screen` → `reviewBody` (`:3204`) → `diffPane` (`:2304`) → `diffLine` (`:2093`).
  - Retired trees are destroyed one frame later (`shellRoots.ts:76`, `destroyRecursively`).
- **Profile split (TUI, large):** ~75% of draw time creates renderables, ~24% describes the tree. Destroying retired trees adds ~20% more on the next frame.
- **Why:** a Diff cursor move also rebuilds Files, History, header and footer: 264 native-backed objects per press.
- **Fix:** keep the panes whose inputs did not change. `mount` already accepts a live `Renderable` (`renderTree.ts:39`). Better still, keep one tree and update properties per pane (header, Files, Diff, History, footer), which fits WF-214's pane split.
- **Expected gain:** 3–5× fewer objects per key. Key → frame should drop under ~8 ms after a pause.
- **Risk:** medium to high. `ShellRoots` hit-grid timing and selection rules assume whole-tree replacement.

### 6. After a pause, the same work costs ~4× more

- **How much:** the same draw takes 19.4 ms when keys are 120 ms apart and 5.2 ms when a profiler thread keeps the process busy (2 runs each, n=90).
- **Why:** after idling, macOS slows the cores or moves the process to efficiency cores, and the antivirus competes for CPU.
- **What to do:** not a code bug. Warm benchmarks understate how a key feels, so finding 5 matters more than its CPU time; benchmark keys with idle gaps.

### 7. Live recapture rebuilds every file's Diff, and the Diff algorithm gives up on large files

- **How much:**
  - Edit → new live identity takes 584 ms on large, 273 ms on hugefile and ~200 ms on small, before the app's refresh reads.
  - `big.ts` (2,000 scattered edits) shows as **39,991 rows**: every line deleted and re-added. A real line diff is ~22,000 rows.
- **Where:**
  - `reviewing/transition.ts:1019` `project` calls `buildReviewDiff` (`diff.ts:220`) for every captured file on every recapture: LCS `appendComparedMiddle` (`diff.ts:166`), `sameDiffLine` (`:124`), and a SHA-256 per row identity (`projectedDiffRow` `:132`).
  - `diff.ts:173` falls back to delete-all plus add-all once (n+1)(m+1) exceeds `MAX_LCS_CELLS` (4M, about 2,000 × 2,000 lines).
- **Why:** the CPU work (~76 ms per recapture on large) is a small share; most of the wall time is Git and re-reading all 300 changed files. The cell cap hurts quality and size more than speed.
- **Fix:**
  - Build each live Diff lazily on its first `review.live-diff` read, and memoize per (old digest, new digest).
  - Skip re-reading files whose stat data is unchanged (`captureWorkingSides`, `capture.ts:649`).
  - Replace capped LCS with Myers O(ND) or histogram diff for large middles.
- **Expected gain:** −10–15% of recapture time now; much more once reads are reused. Myers turns the 40,000-row rewrite into a readable diff.
- **Risk:** medium. Row identities and anchors change only for files over the cap.

### 8. With a Review open and nothing happening, the runtime keeps checking

- **How much:** 70 Git processes per 20 s and 1.1–1.4 s of runtime CPU per 20 s on large (~6% of a core, plus Git's own CPU). With a stale index each tick costs ~0.4 s of Git.
- **Where:** `projection/index.ts:586` `#startLiveFallbackTimer` with `LIVE_FALLBACK_VERIFICATION_MS = 2_000` (`limits.ts:39`). Each check is 7 processes: `inspection.ts:33` `withGitInspection` builds a fresh overlay (`gitProcess.ts:711`) and runs the config checks (`:829`) every time.
- **Fix:**
  - Gate the tick on a cheap stat probe: `.git/index`, `HEAD`, and the captured files' stat witnesses, which already exist since PERF-03. Run the full status only when the probe shows a change.
  - Cache the overlay and config-check result per config mtime.
  - Merge the two `rev-parse` calls.
- **Expected gain:** ~90% less idle CPU, and 60 → ~25 ms floor per real check.
- **Risk:** low to medium. A stat probe can miss same-size, same-mtime edits; keep an occasional full check.

### 9. Memory: no leak, but the runtime is large

- **TUI:** no retired-tree leak. Heap and object count stay flat over 4,800 keys. RSS climbs ~130 MB over the first 600 draws, then plateaus. That is the memory allocator's high-water mark from object churn, which finding 5 would also cut.
- **Runtime:** holds 450–580 MB RSS with only ~100 MB in JS heap and buffers. The remaining ~400 MB is native and not yet explained: likely the SQLite worker's own heap plus fragmentation from per-read buffers.
- **Next step:** a `vmmap` or heap-snapshot pass on the runtime. APP-03 (caches that never evict) was not exercised in these runs.

### 10. Small CLI costs

- `--version` imports the whole `doctor.js` graph (`developerExecutable.ts:95`): 123 ms against a 27 ms floor. Without `--experimental-ffi` it re-executes itself (+42 ms).
- **Fix:** move `productVersion` into a tiny module.
- **Expected gain:** ~80 ms on `--version`.
- **Risk:** none.

## Quick wins vs larger changes

**Quick wins (small, contained, low risk):**
- Cache the snapshot status per Snapshot and live generation (2).
- Treat the capture adopted at start as verified, and overlap the open reads (1).
- Build the search index from whole-side reads, and validate each digest once per worker call (4).
- Gate the 2 s fallback on a stat probe, cache the inspection overlay, and merge the `rev-parse` calls (8).
- Lighten `--version` (10).

Together these should bring a large-repo open from 1.4 s to ~0.9 s, a cold search from 2.7 s to ~0.2 s, and most refresh reads from 150 ms to ~1 ms.

**Larger changes:**
- Persistent screen tree with per-pane updates (5); best done with WF-214.
- Private refreshed index copy (3).
- Myers or histogram diff, and lazy, memoized live Diffs (7).
- Explain the runtime's native memory (9).

## Not covered

- **Many Messages:** Messages are created only through a connected agent's Send. The draft command now needs the historical "active" Review state that tests install by hand, so 200 Messages could not be seeded from the probe. Measuring this needs the `probe-dogfood.mjs` scripted Pi host.
- **Edit → screen:** timed to the new live identity, not the redrawn frame.
- **Linux:** not measured; figures are medians with p90 or min–max.
