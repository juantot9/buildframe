## Decisions so far

- **Presentation (2026-09-07, user-approved):** rich rendering — tree-sitter syntax highlighting through the existing `code` and `diff` components, and `markdown` where Question bodies adopt it — defaults **on** in the Reviewing TUI whenever the pinned renderer supports it. The terminal-safe ASCII/no-color presentation remains a fully functional, explicitly selectable fallback whose structure the scripted scenarios continue to assert in both modes. Capability is determined by the pinned renderer, not a settings surface. (Amended 2026-09-07, user-approved: token colors join the existing theme definition as described in the grilled implementation decisions below — rich-mode *engagement* itself stays non-configurable.)

- **Component mapping (2026-09-07, pre-implementation):** the settled per-row renderable model in `apps/neoflow/src/reviewingView.ts` — stable `rowIdentity` ids, selection, pointer targets, focus — is load-bearing and stays; rich rendering swaps only the inner code label of each diff row. The mapping:
  1. *Selected diff → per-row `CodeRenderable`.* In rich mode each visible diff row renders its exact decoded bytes through a `CodeRenderable` (`filetype` derived from the projected file path, `SyntaxStyle` derived from the existing `SemanticTheme`, one shared process-wide `getTreeSitterClient()` created lazily and destroyed with the renderer per the lifecycle docs). Add/del row backgrounds, sign colors, selection, and gutter stay on the row Box; the renderable adds only token foreground styling. Accepted trade-off: per-row highlighting loses multi-line token context across row boundaries (a string/comment spanning rows degrades to unstyled on the continuation) — honest per-item degradation, never substitution.
  2. *Question bodies → markdown-highlighted text, not markdown rendering.* Question bodies are immutable exact Draft text, so they render with tree-sitter `markdown` highlighting and `conceal: false` (every byte stays visible) rather than `MarkdownRenderable` structural rendering, which would conceal or reflow characters and present interpreted markup instead of exact content.
  3. *Bundled grammars only; no network.* Filetypes are restricted to the bundled descriptors (typescript/typescriptreact/javascript/javascriptreact/markdown/zig). Remote parser/query URLs are out — they would violate the bounded, no-network inspection posture. Unknown or unconfigured filetypes render the existing plain label.
  4. *Fallback triggers, each degrading visibly to the exact current presentation:* `presentation.noColor` (rich never engages; the settled no-color lane stays byte-identical), unsupported filetype, tree-sitter worker unavailable, parser load failure, or highlight error. `ascii` glyph substitution is orthogonal — rich colors may apply with ASCII glyphs; only `noColor` suppresses all color.
  5. *Boundedness and budgets.* Highlighting processes only already-admitted bounded window content (64-row diff windows, question body rows) decoded from projection `bytesBase64` — no file re-reads, no Git access, no new dependency class (`web-tree-sitter` is already an exact-pinned 0.25.10 peer of `@opentui/core` in the lockfile). Async highlighting renders unstyled first (`drawUnstyledText`), preserving pending-frame truth and the settled user budgets.
  6. *Scenario plan.* Scripted Terminal scenarios gain: rich-by-default styling assertions on a TypeScript diff row; byte-identical no-color assertions unchanged; unsupported-filetype plain rendering; worker-failure visible degradation without error surfacing; reflow/focus/pending-behavior on the rich path; and wide CJK/emoji characters in a diff row asserting display-cell-accurate column alignment and wrap heights on both the rich and fallback paths. The dogfood risk probe must prove worker lifecycle (spawn and destruction with the renderer) plus rich rendering and fallback in the compiled assembly.

- **Display-cell measurement fix (2026-09-07, user-approved, folded into this task):** `clippedCode` and `wrappedDiffRowHeight` in `apps/neoflow/src/reviewingView.ts` currently measure by code-point count (`[...code].length`), but the pinned renderer lays out by display cells, so wide CJK/emoji characters misalign diff columns and wrap-height math under-counts. Measurement switches to display-cell width. Folded here because it is the same per-row rendering path this task reworks, highlighted spans compound the misalignment, and fixing it after rich content lands would force re-verifying both presentations twice.

- **Grilled implementation decisions (2026-09-07, user-approved):** the implementation plan, stress-tested decision by decision before any code:
  1. *Highlight cache.* Content-addressed: key = filetype + SHA-256 of the row's exact decoded bytes, value = token spans; bounded well past the 64-row window. Negative entries (highlight failure → plain) share the same bound so a failing parser never retries per keystroke.
  2. *Async resolution.* Worker results resolve into the cache followed by one `renderer.requestRender()`; live renderables are never mutated and there are no per-renderable completion callbacks. A row renders styled from cache in one pass or unstyled until the next pass; a "stale" result is harmless by construction (stored under a digest).
  3. *Single seam.* One rich-vs-fallback decision point per surface, so the five fallback triggers stay enumerable in one place.
  4. *Display-cell measurement.* A self-contained helper in the app — `Intl.Segmenter` grapheme segmentation plus a compact East Asian Wide/Fullwidth and zero-width table, golden-table tested — powers cell-based `clippedCode` slicing and `wrappedDiffRowHeight`; no new dependency and no in-process claim of universal terminal fidelity (acceptance bar: alignment and self-consistent wrap heights in the scripted terminals).
  5. *Grammar coverage.* Exact-pin `tree-sitter-wasms` 0.1.13 (local wasm bytes from `node_modules`, zero runtime network). Starter allowlist: bundled six (typescript/typescriptreact/javascript/javascriptreact/markdown/zig) + python, go, rust, c, cpp, java, json, yaml, toml, bash, html, css, vue (Vue with injections attempted; degrades to plain if unsound). Angular is covered without a framework grammar via the `.ts`/`.tsx` and `.html` mappings. Svelte and Astro are out of scope — they degrade to plain; extending the allowlist later is a small follow-up. The collection ships wasm only: the first implementation step is a queries-sourcing spike, and the shipped allowlist is exactly what survives it, closed in the resolution. The app's own extension map stays the single source of truth for fallback decisions (lowercase extension lookup, unknown → plain); renderer-internal inference is never trusted for the fallback.
  6. *Token palettes (amendment to the presentation decision).* The existing `ReviewingThemeDefinition` gains optional strictly validated token-color slots; old config files parse unchanged. All three presets (`QUIET_GRAPHITE`, `WARM_CARBON`, `INDIGO_NIGHT`) declare palettes designed to fit them; custom themes override any subset with fall-through to the preset palette, then to the row's kind foreground; captures outside the palette categories always fall through. Rich-mode engagement itself stays non-configurable. No new built-in preset themes in this task — a future preset is purely additive (a frozen theme object plus an `inherits` value).
  7. *Client lifecycle.* The tree-sitter client is owned by `OpenReviewingApplication`, created lazily on the first render pass that wants rich highlighting, and destroyed in `stop()` beside `renderer.destroy()`. Client-creation or worker failure latches once per session — rich is off for the session and everything renders exactly like today (the recorded worker-unavailable fallback; no error banner).
  8. *Bodies and responses.* Per-row markdown highlighting of the already-wrapped discussion rows through the same seam as diff rows; block structure crossing a wrap boundary degrades to unstyled on the continuation (the recorded per-row trade-off). Pi responses get the identical treatment — same surface, same seam; the card never renders its two text surfaces differently.
  9. *Scenario assertions.* Every rich-path scenario asserts dual truth: `captureCharFrame()` text byte-identical to what the fallback lane renders for the same content (rich adds color, never characters), plus `captureSpans()` styling asserted through the theme vocabulary rather than raw SGR codes. The no-color lane's byte-exact assertions stay untouched.

  Standing guidance recorded with these decisions: they remain adjustable during development and manual dogfooding — real feedback from use outweighs any recorded choice here, and each adjustment is noted in this issue when made.

## Resolution (2026-09-07)

**Shipped grammar allowlist — exactly what survived the queries-sourcing and asset-compatibility probes.** Eighteen filetypes: the six bundled by `@opentui/core` 0.5.10 (typescript, typescriptreact, javascript, javascriptreact, markdown, zig) plus twelve sourced from exact-pinned local packages (python 0.25.0, go 0.25.0, rust 0.24.0, c 0.24.1, cpp 0.23.4, java 0.23.5, json 0.24.8, yaml via `@tree-sitter-grammars/tree-sitter-yaml` 0.7.1, toml 0.5.1, bash 0.25.1, html 0.23.2, css 0.25.0). Every non-bundled grammar is registered from local `node_modules` wasm + query bytes; zero runtime network. cpp chains the c highlights query; html ships its injections query; markdown keeps its bundled injections so fenced TypeScript/JavaScript inside Pi Responses highlights.

**Probe results recorded for provenance.** `tree-sitter-wasms` 0.1.13 ships wasm only (no queries); grammar npm packages ship matching highlights queries. A live `TreeSitterClient` probe against every registered filetype exposed two wasm/query version mismatches: the collection's rust wasm (built from tree-sitter-rust 0.20.x) rejects the 0.24.0 queries, and the collection's vue wasm rejects the maintained fork's queries ("Bad node name"). Fix for rust: use the grammar package's own wasm. **Vue is therefore dropped from the shipped allowlist** and degrades to plain text under the recorded "degrades if unsound" rule; the extension map never maps `.vue`, and `.svelte`/`.astro` remain out of scope. Provenance of the abandoned vendored Vue queries: `tree-sitter-grammars/tree-sitter-vue` MIT fork at commit `7e48557b903a9db9c38cea3b7839ef7e1f36c693` (fetched, probed, rejected, deleted — not shipped).

**Implementation adjustments to recorded decisions (both user-approved 2026-09-07 before landing):**

1. *Highlight delivery via cached spans, not per-row `CodeRenderable`.* `highlightOnce(content, filetype)` returns `[start, end, group]` spans — exactly the cache's shape — and `treeSitterToTextChunks(content, spans, style, { enabled: false })` converts them synchronously into `StyledText` chunks; only the inner code label swaps (same seam, all recorded invariants hold). No per-row parser buffers, so the "never mutate renderables, cache-fill + requestRender" decision is literally true. `conceal: { enabled: false }` keeps every markdown byte visible. The converter output is verified byte-identical to the input and fails closed to plain text otherwise.
2. *Per-application `new TreeSitterClient({ dataPath })` + `await destroy()` instead of the global singleton* — the global client is process-wide, but the scenario harness creates multiple application instances per process. The client is created lazily on the first rich render (Home never starts the worker), destroyed in `stop()` before `renderer.destroy()`, and one creation/worker failure latches rich-off for the session.

**Additional implementation facts recorded during landing:**

- OpenTUI workers create `<dataPath>/tree-sitter` directories even when every parser and query is a local file, so the application owns a temporary cache directory (`mkdtemp`) and removes it after client destruction; no application data path is ever written.
- Token groups are mapped onto the palette vocabulary through a closed capture-role map (text/heading → markup, boolean → constant, attribute → property, delimiter → punctuation, constructor → function, float → number); captures outside the map fall through to the row's kind foreground via the style's `default` slot. The three presets declare palettes; custom themes override any subset; strict validation rejects unknown roles and non-`#rrggbb` values while old configs parse unchanged.
- Display-cell measurement (`Intl.Segmenter` graphemes + compact Wide/Fullwidth and zero-width tables, golden-table tested) powers `clippedCode`, `wrappedDiffRowHeight`, and side-by-side heights, and pane-width estimation now matches real layout content widths; `Intl.Segmenter` is provided by Node 26.
- Highlight results are content-addressed (filetype + SHA-256 of the exact decoded bytes), bounded at 1024 entries with in-flight entries never evicted; per-filetype parser preloads latch failures; pending and failed rows render exact plain text; late completions after shutdown are ignored.
- All five fallback triggers stay in one seam (`ReviewingHighlight.text`): no-color, unsupported filetype, worker/creation failure, parser or highlight failure/warning, and pending.

**Verification.** Full lane 34 files / 285 tests, typecheck, build, smoke, State/Runtime/Pi probes, rebuilt dogfood probe (worker lifecycle: lazy start, no-buffer retention, awaited destruction, cache removal; rich Diff through the compiled assembly; byte-identical no-color frame), dependency firewall with the exact-pin rule for parser assets, and `git diff --check` all pass. The dogfood fixture's reviewed file is now `review.ts` so the compiled probe exercises a real allowlisted filetype.

## Outcome

The Reviewing TUI gains rich content rendering built on the capability surfaced by WF-194 — tree-sitter syntax highlighting or OpenTUI's current rich-content mechanism, whichever the release inventory shows is the supported path — applied first to the surfaces where it serves review truth: the selected-diff code view and Question bodies. The presentation decision is settled explicitly before implementation: the settled scripted-Terminal posture asserts no-color/ASCII-only output as the safety floor, so this task must record where color and rich styling are permitted (for example, capability-detected with rich rendering defaulting on for capable terminals), how the terminal-safe ASCII/no-color fallback path remains fully functional and visibly equivalent in structure, and how scripted scenarios assert both presentations coherently. Rich rendering is presentation-only: exact content bytes are never re-decoded lossily, binary and unrenderable content stay unrenderable, parsing runs only on already-admitted bounded slices (never eagerly over unbounded files), and any render or parse failure degrades visibly to plain text rather than blocking or silently substituting.

## Interface

No Workspace Interface, State format, record format, limit, deadline, or budget changes. Semantic identities (Review, file, diff row, Question, Anchor, Batch) are unaffected by presentation. The only product delta is inside the `apps/neoflow` presentation layer: how admitted content slices are rendered, plus any closed application-level presentation facts needed to express the capability decision (for example, a rendered-mode fact that scripted scenarios and the launcher harness can assert). Content projection envelopes keep returning exact bytes and their settled availability/limitation facts; rich rendering is derived at render time from those exact bytes.

## Module seam

Presentation lives in the Reviewing Application (`apps/neoflow`); Workspace Evidence, Projection, Reviewing, and Harness Interaction keep their settled seams and are changed only if a defect is exposed, in which case the fix is folded into the owning owner and re-proved. The application continues to consume only the closed Workspace Interface plus the pinned `@opentui/core`; tree-sitter or any new parser dependency is confined to the application package and must pass the dependency firewall.
