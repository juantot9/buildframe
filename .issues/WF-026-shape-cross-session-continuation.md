## Question

What is the complete v1 Continue in Another Session lifecycle—from choosing an eligible point in an existing Workflow, selecting and validating a fresh Pi or Claude Code destination, curating and committing the exact Continuation Brief, and using the strongest honest route through attachment transition, start, settlement, cancellation, failure, unresolved prior activity, restart, and recovery—without transferring conversation state, rewriting prior Invocation evidence, or implying semantic continuation the destination cannot prove?

## Resolution comment

**Continue in Another Session** is a scoped orientation action inside one existing Workflow, not a successor Workflow, Workflow Resume, session migration, or generic Chat escape hatch. The user selects one exact **Continuation Point** and one fresh Pi or Claude Code destination; commitment creates an immutable **Continuation Brief** and a dedicated discussion-only **Continue Workflow Handoff**. The Handoff carries no inherited mutation, generation, Feedback, Review Batch, Plan Approval, or implementation authority. Any such next step still uses its existing action-specific decision and Workflow Handoff with all normal prerequisites. Continuation therefore makes durable Workflow context portable across sessions without making the destination authoritative over Workflow state.

A Continuation Point is a user-selected durable semantic position in the owning Workflow: one exact primary Artifact or committed milestone together with the Workflow goal, current lifecycle position, unresolved committed items, and relevant Invocation or Offer evidence at the time of commitment. Neoflow may suggest the most recent actionable point but never chooses one merely from the focused pane, newest Harness message, session recency, content similarity, or current attachment. A historical Artifact may be selected for emphasis, but later Approval, Completion, withdrawal, disposition, Handoff, cancellation, and evidence facts remain visible and cannot be omitted to simulate rollback. Harness transcript position, model memory, cursor state, streams, tool activity, and other ephemeral state are never eligible points.

The owning Workflow must already contain durable Harness-facing activity—an exact Handoff, Manual Handoff, associated Harness Offer, or correlated Invocation—and its current lifecycle must permit further Planning or Reviewing work. A locally prepared Workflow with no prior external context uses its ordinary first Handoff instead. A cancelled Workflow must cross its existing restore or reopening boundary, completed Planning must either reopen for revision work or use the separate eligible Implementation Handoff, and a completed Review must open its successor Review Pass; Continue cannot perform those transitions implicitly. Archive remains organizational and cannot weaken those semantic prerequisites. Trashed, quarantined, cross-workspace, missing, or truth-critically incoherent source records are ineligible until restored, recovered, imported and rebound, or otherwise made valid through their existing lifecycle.

Brief curation is explicit and source-backed rather than an AI-generated transcript summary. Neoflow deterministically seeds the compact goal, current position, and unresolved-item facts from durable Workflow records; the user may correct the framing, add one explicit transition note, and select exact Artifacts and accepted context captures. Mutable drafts never acquire committed authority merely by appearing in a Brief, and exact payload rules must label any deliberately frozen descriptive draft material as such. The preview shows every selected record, current-versus-historical role, source and provenance, ordering, exact context-budget counts, unavailable or unrepresentable item, exclusion, and sensitive marker. It never reads or summarizes Harness transcripts, copies hidden conversation state, resolves live Context Locators silently, adds ambient workspace or editor content, or treats observability as context.

A fresh correlated destination means an Attachment Identity distinct from the source session and revalidated for the same canonical Workspace Identity. The user starts the Pi or Claude Code session; Neoflow may discover it, but never launches, clears, closes, ranks, or automatically chooses it. Attachment Establishment and an explicit switch disclose no Brief content and affect only future work. A known checkout mismatch is a blocker, not an override. When Manual Handoff is used without a live Attachment, the declared Pi or Claude Code session may still be the destination, but Neoflow labels its identity and freshness as user-declared or unverified rather than pretending it established a new session.

The Harness Interaction Module selects only the strongest honest route for the dedicated Continue Workflow Handoff. In v1, a validated fresh Pi Attachment uses Direct with the cooperative request-scoped read-tool gate, observed start and settlement evidence, and Direct Request interruption. A Claude Code continuation uses Manual Handoff: the proven Review User Pull and native Plan Offer gate are specific to their existing Handoff and Offer contracts and cannot be repurposed as a generic continuation route. A later Claude Plan Offer is a new occurrence requiring explicit Offer Association; a prior Brief or Manual Handoff is only candidate context and never correlation or consent. Manual is prominent when it is the sole compatible route and is an explicit Capability Downgrade when a stronger Pi Direct route was available. No route is chosen from model preference or Context Budget Evidence.

The accepted curation, Continue Workflow Handoff, destination-scoped Commitment Receipt, and route-specific record commit atomically before any external effect. Pi Direct creates one Invocation in `awaiting start`; Manual Handoff durably creates the exact human-carriable material in `Ready to carry` before reveal. A failed Durable Commit leaves no Brief, Handoff, Invocation, manual material, or external contact. Duplicate handling of the same command is idempotent. Editing the goal, point, unresolved items, transition note, selected records, authority, or destination after commitment requires a new Brief or Handoff as appropriate; an exact resubmission reuses the immutable originals.

Pi submission or bridge acceptance proves no start. Correlated start advances only that new Invocation; normal end, failure, interruption, rejection, or unresolved outcome follows its frozen Evidence Profile. Settlement proves neither that the destination understood the Brief nor that Planning, Reviewing, implementation, or any unresolved item advanced. The Continue Workflow Handoff has no Artifact Result Contract, so Harness output remains in the destination-owned conversation unless a later existing contract independently materializes an Artifact. Attachment loss, session replacement, a cancellation race, or restart with missing terminal evidence follows the normal conservative unresolved rules. Interruption intent never changes status by itself.

Manual continuation creates no Invocation and no awaiting-start, active, failed, settled, or unresolved Harness status. `Ready to carry`, `Shown`, `Copied locally`, and local presentation failure retain their already-defined meanings; external use stays unverified rather than becoming an unresolved Invocation. A later Artifact, workspace change, Harness Offer, or human decision may reference the Brief but cannot retroactively prove that the destination received, understood, or acted on it.

Existing source-session authority and evidence never move. Selecting or switching attachments does not rewrite an old Preparation, Offer, Handoff, Invocation, Attachment Identity, Capability Snapshot, or receipt. An open User Pull Preparation follows its own claim, withdrawal, or semantic-expiry race; if a switch disproves its bound identity, expiry records that fact, while a claim that commits first creates the old Invocation normally. A live Harness Offer remains independently awaiting decision or fail-closed expiry. Awaiting-start, active, or unresolved prior activity is named with its destination and last trustworthy evidence. Repeating the same immutable Handoff uses Explicit Resubmission and its duplicate-execution gate; committing a different Continue Workflow Handoff uses the composed overlap gate. Neither path deadlocks the user or clears the earlier history.

Leaving curation before commitment has no external effect. After commitment, the Brief, Handoff, receipt, and evidence are immutable: Workflow Cancellation may archive the Workflow, withdraw an open Preparation, or pursue the applicable Interruption Route, but it cannot withdraw already disclosed material or establish a Harness outcome. Route rejection, failure, unavailability, or unresolved evidence never triggers automatic retry, replay, fallback, attachment change, or Manual Handoff. Another attempt is either an exact Explicit Resubmission or a new destination-scoped commitment, preserving every prior attempt.

Restart reconstructs only durable Workflow, Brief, Handoff, destination, receipt, Preparation, and Invocation records. It never reopens a Harness conversation, chooses or reattaches a session, reveals manual material, resends a Handoff, or upgrades missing evidence. Uncommitted curation returns only to the extent ordinary draft persistence proved it durable and must be revalidated against current source records and destination evidence before commitment. Corrupt Brief or Handoff records enter the smallest possible Recovery Quarantine while unaffected Workflow history remains readable.

The truthful success boundary is the local commitment and its route-specific facts, never one blanket `Continued` state. Exact Continue Workflow payload fields remain for [Define v1 Workflow Handoff payload contracts](./WF-031-define-v1-workflow-handoff-payloads.md), and Home placement and semantic return priority remain for [Shape Home attention and Workflow Resume](./WF-028-shape-home-workflow-resume.md). This resolution sharpens canonical language in [`CONTEXT.md`](../CONTEXT.md) and the conceptual Harness Interaction Interface in [`docs/blueprint/harness-capability-seam.md`](../docs/blueprint/harness-capability-seam.md); it surfaces no new ticket or fog.
