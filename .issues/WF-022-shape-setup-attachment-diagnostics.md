## Question

How should a developer install and verify Neoflow’s Pi, Claude Code, and Neovim integrations and establish, inspect, switch, detach, and recover the one active Harness and Editor attachments—including absent or competing sessions, checkout mismatches, missing or incompatible bridges, and degraded health—without treating attachment as workflow consent?

## Resolution comment

Neoflow uses a documentation-first setup contract rather than a mandatory in-app wizard. Versioned product documentation is canonical for prerequisites, exact installation, upgrade and removal steps, supported Pi, Claude Code, and Neovim versions, platform-specific configuration, verification walkthroughs, and deeper troubleshooting. Each integration is independently optional at product entry, and Neoflow remains usable when one or more are absent. Home, contextual workflow failures, help, and a dedicated **Connections & Diagnostics** view care for users who did not follow the documentation by naming the exact condition, showing what remains usable, offering the shortest corrective action, and linking directly to the relevant guide section rather than a generic manual.

In-app assistance is diagnostic and explicitly reparative rather than passive or silently self-healing. When Neoflow can make a safe, bounded, reversible change to its own bridge registration or a fully understood additive configuration, it may offer one user-invoked repair that previews every affected setting or file, preserves existing configuration, and reports the result. It never silently installs or upgrades Pi, Claude Code, or Neovim; overwrites unfamiliar configuration; changes a tool's checkout; launches, terminates, or chooses a user session; or weakens a compatibility requirement. Failed repair leaves the prior configuration intact. Repair itself grants no attachment: it triggers fresh verification, after which the configured attachment-selection policy may apply.

Integration Health is a layered evidence account, never one green `connected` Boolean. The view distinguishes installation and supported-version compatibility; bridge reachability and contract or Capability Manifest validity; discovered Attachment Candidates; session or editor identity; canonical-checkout fit; the selected active attachment; Handoff-specific capability and current Availability; and optional observability or lifecycle-evidence freshness. Each layer shows its evidence source, last observation, exact failing condition, workflow impact, and next action through progressive detail. Optional telemetry loss degrades only that evidence. A valid Attachment Identity may remain selected while an individual route is blocked, unknown, unsupported, stale, or not yet exercised; bridge, identity, checkout, or manifest failure blocks only commitments whose required truth cannot be established. No layer implies workflow consent, semantic correctness, or readiness of another layer.

Normal verification is non-invasive. It may inspect local installation and configuration, validate versions and manifests, handshake with bridges, revalidate identity and canonical checkout, and perform bounded protocol round trips, but it sends no model request, discloses no workflow context, mutates no workspace, moves no editor, and manufactures no Native Gate Offer. If end-to-end verification genuinely requires visible harness or editor activity, Neoflow offers a separately labelled user-initiated test that previews the exact turn, navigation, or other effect. Until that happens, diagnostics say `not yet exercised` rather than manufacturing evidence. Setup success therefore means only that the checked layers passed; every real Workflow Handoff still performs atomic identity, capability, availability, route, payload, and consent revalidation.

A bridge may advertise an Attachment Candidate using only the minimum compatibility, live-session or editor-instance identity, canonical-checkout, and correlation metadata needed to evaluate it. Candidate discovery shares no workflow content and creates neither an Attached Harness nor an active Editor Companion. The Connections view clearly separates candidates from selected attachments and presents recognizable destination labels: integration name, stable local session or instance label, repository label, canonical checkout root, and connection state. Current cwd, model, raw process, transport, and machine identifiers remain supplementary local diagnostics rather than primary identity or destination claims.

Neoflow permits one selected Harness attachment and one selected Editor attachment for the active Workspace Identity. User Configuration independently provides `ask` and `auto-attach-unique` selection policies for Harness and Editor, with `ask` as the default. `auto-attach-unique` applies only when exactly one candidate has a compatible validated bridge, a valid identity, and the same canonical checkout; route-specific Availability is still evaluated separately. Zero or multiple eligible candidates always require a chooser, and Neoflow never selects the most recent, foreground, nearest-cwd, or otherwise guessed candidate. The portable policy contains no Workspace or Attachment Identity. Exact selected identities and their history remain private workspace-scoped state.

Absent integrations remain visibly unattached with installation and verification actions. Missing or incompatible bridges show the detected and supported contracts and offer update or repair guidance; unknown or malformed guarantees can never be enabled by user configuration. Checkout-mismatched sessions remain visible, non-attachable candidates for the current Workspace, with actions to open Neoflow for that checkout or correct the external tool explicitly—never an override or silent cwd change. Competing matching sessions receive stable labels and explicit selection. Losing an attachment leaves it lost and never fails over, even under `auto-attach-unique`.

Switching and detaching are explicit actions regardless of selection policy and affect only future destinations. Existing Harness Offers, Offer Decisions, prepared User Pulls, Workflow Handoffs, Invocations, receipts, and evidence remain immutably bound to their original Attachment Identity; none migrate or inherit consent. After a switch, Neoflow may continue collecting correlated lifecycle evidence from the old bridge while it remains reachable, but sends no new work there unless the user selects it again. Identity-bound prepared routes expire or become unavailable according to their own lifecycle. A switch does not dismiss unresolved work, and starting potentially overlapping work elsewhere uses the existing unresolved-activity guardrail.

Detaching while an Invocation or gate may still have an external effect receives one focused consequence gate naming the exact activity and last trustworthy evidence. Detachment does not request or prove harness interruption; if correlation is lost, the Invocation or decision delivery remains unresolved unless later Terminal Evidence or route-specific reconciliation proves otherwise. Editor switching similarly retains immutable Editor Context Contributions, Artifacts, Anchors, drafts, and acknowledged command history, but transfers no Presence, dirty-buffer match, navigation, Editor Return Location, Editor Target validity, or consent to the new Editor Attachment.

Startup, transport reconnect, bridge repair, and relevant configuration change perform fresh checks rather than trusting prior health. A reconnect retains the selected Attachment Identity only after the exact same live session or editor instance and canonical checkout are revalidated. A changed session or checkout is a new candidate, not recovery; reconnect never substitutes it, restores expired consent, replays navigation, resends a Handoff, resumes an Invocation, or fills missing evidence. Previously committed workflow records remain available, while route-specific recovery stays conservative and visible through the existing Recovery Summary.

The shipped guides and contextual checks apply this common contract to each reference integration without claiming parity. Pi setup verifies the reviewed extension bridge in the exact user-owned session and checkout while leaving Direct route readiness and settlement to live evidence. Claude Code setup verifies the reviewed plugin, hooks, bridge, and namespaced User Pull action, while Native Plan readiness exists only for a live correlated Offer and no foreground busy, push, cancellation, or replay guarantee is invented. Neovim setup verifies a registered persistent companion and exact checkout round trip without treating editor Presence as context. At every layer, installation, bridge reachability, candidate discovery, attachment, Handoff Availability, workflow consent, external start, and correlated outcome remain truth-critical distinct facts.
