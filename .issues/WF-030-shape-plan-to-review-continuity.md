## Question

What is the complete v1 path for starting and conducting a Review from an Implementation Handoff—including eligibility among Approvals and Handoff attempts, present, deliberately absent, stale, or unverified Implementation Baselines, exact Change Set selection, independent Planning and Reviewing lifecycles, approved Plan Revision inspection and Plan Anchor evidence, cancellation, restart, and archival—and what dependency closure, exact disclosure, external-reference behavior, import, and Workspace Rebinding rules preserve that cross-Workflow relationship in Portable Workflow Bundles without attributing changes to the Harness or turning the Plan into tasks, mappings, progress, or compliance claims?

## Resolution comment

Plan-to-Review Continuity is one immutable cross-Workflow relationship created when a new Review starts from one exact Durable-Committed Implementation Handoff. The relationship binds the Review, source Handoff, consumed Plan Approval, exact approved Plan Revision, the Handoff’s complete Implementation Baseline or its recorded absence, and the Review’s exact Change Set intent. It is provenance and supporting context, not a live coupling: no later state in either Workflow rewrites it.

An Implementation Handoff is eligible as soon as its own Durable Commit exists and every referenced local record is intact. Planning Completion or Plan Approval without a Handoff is not eligible. Direct, User Pull, Native Gate, and Manual Handoffs are equally valid local continuity sources; an unclaimed Preparation, awaiting-start Invocation, proven no-start, active, ended, failed, interrupted, unresolved, or manually unknowable external outcome changes the evidence shown but not the Handoff’s eligibility. This does not imply that implementation started or occurred. Planning Cancellation, Archive, Reopening, a later Plan Revision, or a later Approval cannot revoke or retarget an already-committed Handoff.

The source chooser deals in Handoffs, not Harness attempts. Explicit Resubmissions and their Invocations remain evidence under the same immutable Handoff. Reopening or recopying one Manual Handoff remains the same source, while an explicitly authorized later Manual Handoff or a materially new correlated Handoff is a distinct candidate. A contextual action on one Handoff selects it directly; when entry begins from the Planning Workflow and several Handoffs exist, Neoflow requires the user to choose the exact one rather than inferring “latest” from time, Plan content, session, or outcome. Each candidate shows its approved Revision, route or Manual destination, Baseline state, and the last trustworthy lifecycle evidence.

`Start linked review` first presents that exact source and then the normal exact Change Set selector. Once selection can be captured coherently, one local Durable Commit creates the Review, its stable Change Set, the Plan-to-Review relationship, and its first Review Snapshot. A failed or incoherent capture reports the exact blocker and creates no apparently usable linked Review. The action itself is the Consent Boundary because it creates no external effect; limitations are visible in the selection rather than hidden behind a generic “review implementation” label.

A complete, integrity-valid Implementation Baseline is the default left endpoint and the current effective working state is the default right endpoint. A Baseline that differs from the current checkout is not disqualified—measuring that difference is the purpose of this comparison—and a current match truthfully yields an empty Change Set. The Review summary says `Changes since the Implementation Handoff baseline`, never `Harness changes` or `implemented Plan`. It shows the owning Workspace, exact Handoff and Baseline, effective-working-state composition, ignored and outside-checkout exclusions, path scope, and every per-file evidence limitation established by [Define the workspace and change-set evidence contract](./WF-023-define-workspace-change-set-evidence.md).

Baseline absence and Baseline unavailability remain distinct. When the Handoff deliberately proceeded without a Baseline, the source stays eligible but Neoflow cannot offer or claim a since-Handoff comparison; the user must explicitly choose one of the ordinary exact Git Change Set bases. When a Baseline should exist but its bytes, integrity, provenance, or Workspace binding cannot be verified, Neoflow names that failure and never reclassifies it as acknowledged absence. The user may recover or rebind it, or deliberately choose an independently exact Git basis; the resulting Review remains linked to the Handoff and approved Plan but carries no implementation-bounded comparison claim. If the current workspace cannot be inspected, Baseline-to-current is unavailable, though another wholly exact locally available comparison may still be selected. No partial Baseline, guessed ref, prior observation, implicit fetch, or inferred checkout equivalence fills a gap.

The selected checkout, comparison basis, compared-state kind, and optional path scope become the Review’s stable Change Set intent. Baseline-to-current is preferred, not forced: a user may deliberately choose another supported comparison when it better describes the work under review, with the loss of since-Handoff bounding stated plainly. Narrowing scope never means the omitted paths complied with the Plan. Refresh resolves only the unchanged intent and captures a successor Review Snapshot; changing the source Handoff, checkout, basis, compared-state kind, or scope creates a different Review rather than rewriting provenance.

The exact approved Plan Revision is always locally inspectable from the linked Review as immutable supporting context, even when Planning is completed, reopened, cancelled, archived, or has newer Revisions. It is not copied into a mutable “current Plan,” and neither Plan lineage focus nor later Approval changes the linked Revision. A Review Finding keeps one authoritative Anchor in its exact Review Snapshot and may cite an exact Anchor in that approved Revision only through an Evidence Reference. The reference preserves the Plan Artifact Identity, side-independent Anchor, selected content, and provenance; it does not enlarge mutation authority, establish a Plan-step-to-code mapping, or create a disposition or progress state on the Plan.

Conducting the Review otherwise follows [Shape the Reviewing workflow](./WF-006-shape-reviewing-workflow.md): immutable Snapshots, explicit Annotation intents, one Review Batch commitment, independent Harness evidence, human Re-review, and one Review Result per pass. Merely attaching the Plan as supporting context grants no Harness disclosure. The exact Plan material and Evidence References carried by a Submit Review Batch remain governed by its immutable Workflow Handoff payload and Handoff Disclosure Preview in [Define v1 Workflow Handoff payload contracts](./WF-031-define-v1-workflow-handoff-payloads.md); an Adapter may not add the Plan, ambient Planning context, or inferred mappings.

The two Workflow lifecycles never cascade. Starting, refreshing, completing, cancelling, archiving, unarchiving, or continuing the Review does not reopen Planning, change its Completion, alter its Approval or Handoff, settle an Invocation, or disposition Planning Feedback. Planning Reopening, new Revisions, Cancellation, Archive, unarchive, and late Terminal Evidence do not stale or retarget the link. Workspace changes may stale the Review Snapshot under its own Change Set; the Plan Revision remains immutable supporting context, and Context Drift remains separate evidence rather than a compliance judgment.

An already-open Review with the same Handoff and identical Change Set intent is resumed rather than duplicated. Continuing a completed Review with unchanged intent opens a successor Review Pass. Explicitly restarting a cancelled Review creates a new Review and relationship while preserving the cancelled history; choosing a different Handoff or Change Set intent also creates a new Review. Process restart reconstructs every link and exact Artifact from Authoritative Workflow State, performs no refresh or Harness replay, and rechecks workspace-dependent evidence before any new Review Batch commitment. Archive changes visibility only. Recoverable Trash preserves the relationship; permanent purge cannot leave a retained Review with a dangling required Planning dependency, so the destructive scope must include the dependent records or the purge is blocked. Exact Home controls remain with [Shape Home attention and Workflow Resume](./WF-028-shape-home-workflow-resume.md).

A Portable Workflow Bundle containing a linked Review must contain the transitive semantic dependency closure needed to validate and use that relationship. At minimum this includes the relationship; source and destination Workflow identities and relevant lifecycle facts; the exact Implementation Handoff and Commitment Receipt; its Approval, approved Plan Revision and anchorable bytes; the complete Baseline or durable absence decision; route, Manual destination, Capability, consent, and Handoff-specific Invocation evidence referenced by the included state; the exact Change Set, Review Snapshots, Results, Batches, Findings, and Evidence Reference targets; and every Artifact byte, source capture, identity, receipt, and provenance record those records require. Closure follows strong references recursively but need not pull in unrelated Planning lineages or other Reviews merely because they share a Workspace.

The Sensitive Export Gate shows the user’s requested Workflows separately from automatically required cross-Workflow dependencies, with exact record and Artifact counts, byte size, source snapshots, sensitive categories, raw local identifiers, and the reason each dependency is included. The user may include more of the Planning Workflow, remove the linked Review from the export, or cancel; v1 never silently strips the link, Plan content, Baseline evidence, Anchor target, or authority record to make a smaller “portable” bundle. A missing, quarantined, or unverifiable strong dependency blocks full-fidelity export. Only optional reverse-navigation or index references may remain external; the manifest preserves their stable identities and provenance and import renders them explicitly unavailable. An external reference grants no authority, supplies no bytes, and is never resolved by content, path, time, or a similarly named local record.

Import validates the whole closure atomically: identities and digests, ownership, Handoff-to-Approval-to-Revision consistency, Baseline state, Anchor targets, receipts, reference completeness, and format versions must agree before any record becomes authoritative. Identical identities and content import idempotently; any identity conflict rejects the import. Original Workflow, Artifact, Workspace, Handoff, Approval, and Invocation identities and provenance remain unchanged. Historical Attachments and Harness activity remain inert.

Workspace Rebinding applies one explicit destination binding to the connected Planning-and-Review dependency component rather than rebinding each side independently or rewriting its origin. A known checkout mismatch blocks the binding. Self-contained Plan Revisions, Baselines, prior Review Snapshots, Results, and Anchors remain exactly inspectable after import, but Rebinding itself proves neither that the destination checkout equals the original nor that old workspace-dependent evidence is current. Existing Snapshots retain their imported verification state until explicit destination inspection; a new Baseline-to-current refresh or Review Batch requires a verified destination and a newly verified-current Snapshot under the unchanged Change Set. A deliberately absent Baseline remains absent, an unavailable one is not synthesized, and no Preparation, Offer, Invocation, or implementation activity resumes.

These rules preserve one governing boundary: the Handoff identifies what the human authorized and the Baseline can bound what changed afterward, while neither fact identifies who changed it or whether the Plan was followed. Neoflow provides no automatic Plan-step mapping, task list, completion marks, progress, compliance score, generated judgment, or Harness attribution. No new ticket or fog is required; bundle payload details, Home presentation, and final blueprint retesting remain in their existing tickets. Canonical Plan-to-Review Continuity language is sharpened in [`CONTEXT.md`](../CONTEXT.md).
