## Question

Which workspace and version-control environments does Neoflow v1 support, which exact comparison bases and compared states may define a Change Set, and how must evidence capture, limits, verification, and degradation treat working-tree and index changes, refs, Implementation Baselines, untracked or ignored content, renames, binary and generated files, symlinks, submodules, large-file indirection, missing objects, and the absence of service-specific pull-request integrations?

## Blocked by

- [Test the blueprint for completeness](./WF-017-test-blueprint-completeness.md)

## Resolution comment

Neoflow v1 supports one local non-bare Git working tree on native macOS, Linux, or wholly within one WSL2 environment. Starting below the working-tree root resolves to that canonical checkout. Ordinary clones and linked worktrees are supported as distinct Workspace Identities; path aliases, moves, and branch changes retain one identity. Non-Git directories, bare or remote-only repositories, other version-control systems, and native Windows checkouts are unsupported. Shallow, partial, and sparse checkouts are usable only to the extent that required local Git and filesystem evidence is available: Neoflow never fetches, hydrates, or guesses missing state. Intentional sparse absence is not a deletion, and nested repositories are separate workspace boundaries rather than recursively captured content.

A Change Set uses a small exact endpoint model. Supported comparisons are exact commit/tree to exact commit/tree; the merge base of a selected locally available ref with an exact commit/tree to that commit/tree; exact commit/tree to index; exact commit/tree to effective working state; index to working tree for unstaged-only review; and Implementation Baseline to current effective working state. A ref selector, merge-base rule, compared-state kind, canonical checkout, and optional path scope remain part of stable comparison intent, while every Review Snapshot freezes the resolved object identities and evidence. Local branches, tags, remote-tracking refs, and detached commits are eligible when locally resolvable. Ref movement, deletion, an unavailable merge base, and unborn-HEAD limitations are exposed rather than replaced with another basis.

Effective working state includes staged and unstaged tracked changes without double-counting and includes non-ignored untracked files inside scope. An index endpoint contains only entries represented in the index. Ignored untracked files are excluded by default and the exclusion is disclosed; a user may explicitly add a bounded ignored path, which is captured and marked as potentially sensitive under the existing Handoff disclosure rules. Tracked files remain included even when an ignore rule matches them. Scope, not renderability, binary classification, generated classification, or file count, controls manifest membership. A new, removed, type-changed, mode-changed, staged differently, or content-changed item inside scope changes the resolved input; excluded ignored items and changes outside scope do not.

Every Review Snapshot preserves a complete, lossless changed-file manifest before applying presentation limits. For each side it records the exact path, kind, Git mode, size, locally available object identity or content digest, staging provenance, availability, and evidence source. Git path bytes and case distinctions remain lossless even when the host requires escaped display or cannot materialize a colliding working path. Timestamps and filesystem observation alone never establish equality. Snapshot capture resolves the selectors and records the index and relevant workspace inputs, captures the manifest and admitted bytes, then revalidates every scope-relevant ref, index entry, path, mode, size, and digest. Relevant movement receives a small bounded retry; if stability still cannot be established, Neoflow preserves diagnostics and any prior Snapshot but publishes no mixed-time successor. Unrelated out-of-scope movement does not interfere.

Manifest evidence, captured bytes, and renderability are independent. Within the agreed release floor of 1,000 changed files and 50 MiB of textual Review content, all locally available textual bytes must be captured. Exact measured per-file and aggregate capture and render thresholds are named, versioned evidence and may be refined during implementation planning under the existing performance criteria. Beyond them, degradation is per file and per side: the manifest remains complete, captured bytes remain immutable, collapsed content remains available, and unavailable or unrenderable content carries an exact reason. Such a Snapshot may remain verified-current when its endpoint identity is exact. It permits manifest navigation and whole-file Annotations, but no range Anchor or viewed claim over unavailable bytes. Any Handoff previews exactly which content it will and will not carry and the resulting limitation. Limits never silently omit a file or globally reject an otherwise resolvable Review.

Binary classification is evidence-based and never uses lossy decoding. Admitted binary bytes remain exact, but v1 promises metadata and exact-byte access rather than a semantic binary diff. Generated status comes only from explicit repository evidence or user classification, never a path guess; generated files remain in scope and may begin collapsed. Rename and copy detection is derived presentation evidence rather than file identity: a Snapshot retains exact old and new paths and content evidence plus the detection method and similarity result. Ambiguous, unavailable, or over-limit detection degrades to additions and deletions without changing captured content or moving Anchors. Old-side and new-side Anchors always remain distinct.

Symlinks are captured as Git modes plus raw link-target bytes and are never dereferenced, including broken links and links outside the checkout. A Git/working-filesystem type mismatch makes the affected working endpoint unverified. Submodules are Gitlinks, not recursively reviewed parent content: Snapshots record before and after Gitlink identities, index state, and, when locally inspectable, checked-out commit and dirty or untracked indicators. Neoflow never initializes, fetches, or updates a submodule. Missing nested checkout state does not invalidate a commit/tree or index comparison whose Gitlink evidence is complete, but makes any dependent working endpoint unverified; reviewing nested source requires that checkout's own Workspace Identity and Review.

For recognized Git large-file indirection, repository pointer evidence and materialized payload evidence remain separate. Neoflow records the exact pointer, declared payload identity and size, local availability, and whether payload bytes were captured. Commit/tree and index comparisons can remain exact from complete pointer evidence without the payload. A working endpoint is verified only when its canonical identity can be derived from local evidence. Neoflow never fetches, hydrates, or uploads payloads implicitly, and local payloads remain subject to binary and capture limits. Arbitrary repository-defined content filters and other indirection are unsupported in v1; Neoflow does not execute them to manufacture evidence and marks dependent working evidence unverified.

Missing structure and missing content degrade differently. An unavailable commit, tree, merge base, or other structure needed to enumerate the complete comparison makes the Snapshot unverified and blocks Review Batch commitment. When complete trees identify every changed path and blob identity but selected blob bytes are absent, the comparison may remain verified-current while those sides are content-unavailable. Missing working files, read permissions, incompatible filesystem semantics, or unstable reads are never reclassified as deletion. Diagnostics name the missing identity or evidence category; the user obtains any required objects outside Neoflow and explicitly refreshes. Caches, refs, hosting services, and prior observations never fill an evidentiary gap by inference.

Workspace Verification is current only when the owning Workspace Identity matches, all required facts are inspectable, every dynamic selector resolves identically, and every scope-relevant identity, mode, staging fact, and digest matches. It is stale when inspection succeeds and any required fact differs, including a ref moving to a different commit even when its tree is identical. It is unverified when equality or difference cannot be established. Fixed endpoints ignore unrelated HEAD and branch movement; exact reversion of every input may make a Snapshot current again. Each check records provenance, but verification remains a projection and never changes immutable Snapshot content.

An Implementation Baseline applies the same evidence rules more strictly to the complete version-control-visible effective checkout immediately before Implementation Handoff. It freezes HEAD/ref or detached/unborn state, index and staging provenance, all tracked paths and content, all non-ignored untracked content, modes, symlink values, and enough retained Git object material and working bytes to reconstruct the baseline without the original checkout or Git objects. Ignored untracked and outside-checkout content remain explicitly excluded; submodules contribute Gitlink evidence and large-file payloads follow the accepted availability policy. The Baseline is checkout-wide rather than inferred from Plan prose. Instability, missing required structure or bytes, or a capture-limit breach creates no partial Baseline; the already-defined explicit proceed-without-baseline path is the only fallback, and branch or ref movement can never alter a Baseline after capture.

V1 has no GitHub-, GitLab-, or other hosting-service pull-request integration. It does not query PR metadata, discover a server target, fetch refs, publish review comments, or claim remote status. A “PR target” in Reviewing means a target ref explicitly supplied by the user or already present and remembered locally for that Workspace; absence falls back to exact local comparison selection, not a service heuristic. The resulting local Change Set, Review Snapshot, Annotations, Review Batch, and Review Result remain complete Neoflow workflow records without a pull request.
